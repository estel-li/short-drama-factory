# 实战制作与诊断

本页把用户提供的 `h3-short-drama-pipeline.zip` 中的制作经验，按当前工厂 2.4.1 的接口与实现重新整理。来源中的机器参数、专用脚本、项目约定和性能归因不作为通用要求；不执行或分发原包脚本。

## 1. 先控制返工成本

把原台词、可改写部分、单镜上限和目标总长区分开。用户给定原句时保持文字与顺序；只有已获改写授权才精简长句。技术预算超限优先调整分镜，不能把提高语速当作通用解决方案。

单镜有 n 句非空台词时，用项目真实 speech_rate/lead/gap/tail 计算：

`所需秒数 = lead + 发音单位数 / speech_rate + max(0,n-1) × gap + tail`

反推上限：`floor((镜长上限 - lead - tail - max(0,n-1) × gap) × speech_rate)`。若剩余时间非正，先改变分配。程序的 spoken_units 不计标点和空白；数字、英文与专业名词的口语长度另行试听，不把“字符”严格等同“音节”。默认 5.6、0.4、0.3、0.55 下，一句台词在 4 秒内约有 17 个发音单位的预算；这只是规划值。

拆镜会重新付出起手和收尾时间，每镜还要做 `17k+5` 帧对齐，**不能承诺拆镜让总生成更快**。应同时检查每镜能否说完、总帧数、GPU 容量和转场是否自然。

若用户指定某段最终为纯色文字页，可降低对底层画面复杂度的要求，但不能自行增加人物、删台词或替换画面。工厂没有通用文字页／尾板自动合成接口；额外制作时另设输出目录和映射清单，详见验收页。

## 2. 场景图与人物身份分开

工厂 `assets.resolve` 会把图片的 `character` 标记传入 Ref2VA 身份校验。这能暴露旧素材把大厅、房间等误当角色的问题，不能据此把整个校验删除。

从 `/api/project/{id}` 的 assets、story.characters、shot.characters 和 bindings 逐一核对：

- 人物图关联真实、已定义的角色 ID，并且该角色确实在镜头里出场。
- 场景／道具图上传时 `character` 留空，角色数组不需要虚构一个“房间角色”来凑校验。
- 不能只凭文件名判断用途；查看素材与用户意图。多人照片、角色扮演道具或拟人角色需要按实际内容处理。
- `characters:[]` 的空镜可以用 T2VA 或适合的参考模式。当前代码不把“Subject 必须是人”作为约束；一台机器出现采样变慢，不能证明原因一定是参考主体非人。

发现确定误标的场景图时，优先采用现有 API 可完成的修法：

1. 确认项目空闲，读取完整 story，记录受影响 UID 与旧素材 ID。
2. 取得原图片文件；可以按 assets 返回的 `file` 从 `/media/{id}/{file}` 下载。上传同图时不传 `--character`，得到新的无角色标记素材 ID。
3. 只替换受影响镜头的 bindings。保持真实角色设定；若原分镜也误把场景当人物，按实际创作意图修正相关 characters 和提示词。不要将大厅补进角色表来绕过身份检查。
4. 调用 validate-story，再 `/api/story` 保存完整对象，复查 prompt 是否被清空。记录素材替换可能引起缓存变化；不直接改 `assets.json` 或 SQLite，也不自动批量清除人物图标记。

`diagnose` 只列出显式绑定中的缺失 ID、角色未出场、未定义角色、缺提示词等线索，不能凭元数据断言某图一定是场景。其绑定计数不包含运行时自动人物参考；首帧接续覆盖手动绑定时，诊断不会把这些被覆盖的槽位当作本次错误。

## 3. 成功镜头作样板，但保留镜头本意

复用已验收镜头的模式、人物及参考契约，可以减少无谓试错。用 `/shots/{uid}/template` 保存样板，读取项目 prompt_templates，在目标镜头填写 `prompt_template_id` 后经 API 保存。应用会核对实际模式、人物、参考摘要，避免把三张图的旧人物定义套进另一组素材。

新镜头重写动作、时间轴和台词；不要为了复制一条成功配置，把空镜改成有人的镜头。模板是候选配置，也不保证采样速度或质量完全一致。

## 4. 插镜、改档与缓存

- 已有镜头的 uid、seed_offset 或显式 seed 保持稳定。id 是位置编号，会随排序改变。
- 向已有项目插镜时为新镜指定未占用 UID，例如 `uuid.uuid4().hex[:20]`；不要沿用旧镜 UID。当前缺省 UID 按项目和位置派生，中间插镜留空可能与原位置镜头冲突。新镜选择独立 seed 或未占用 seed_offset。
- 保留 UID 是复用缓存的必要条件之一，不是保证。提示词、素材、模型、种子、尺寸、步数和前镜末帧依赖改变仍会影响结果；插镜后重新核对相邻接续关系。
- profile 是**项目级**设置，会影响该项目受影响镜头。不要为几个镜头来回切档并承诺保留所有缓存；需要不同渲染方案时先说明代价，必要时采用另一个项目版本。
- 普通创作任务不顺带升级引擎。确需升级时先保存项目和版本，核对模型指纹、图结构、canvas/frames 计算及依赖变化；文件字节变化本身不等于所有缓存必然失效，以实际契约与签名为准。

## 5. 慢渲染的诊断顺序

```powershell
python scripts/factory_api.py diagnose --project PROJECT_ID
python scripts/factory_api.py watch --project PROJECT_ID --job JOB_ID --seconds 45
```

diagnose 返回每镜 UID、计划帧数、记录状态、实际原片帧数和已完成采样阶段耗时。只有同一记录的采样任务 ID 匹配、原片完成且实际帧数存在时，才计算 `recorded_seconds_per_frame`；旧记录／缺数据为 null。耗时属于历史完成记录，**不是当前采样已经耗时**。即使当前 duration 已改，也不会用新帧数除旧耗时。

比较时尽量固定 GPU、显存／内存、模型量化、画幅、步数、模式、参考数量、帧数范围、卸载设置和缓存冷热。按相同阶段耗时比较多条成功样本，再判断是否明显偏离自己的基线。每帧耗时也会随序列长度变化；不沿用来源机器的 3.2～4.2 秒/帧、6 秒告警或 90W 阈值。

观察任务、ComfyUI 对应 prompt 的队列／历史、当前阶段和硬件状态。采样结束前没有 MP4、日志暂时不增长、磁盘没有读写或瞬时功耗低，都不足以说明卡死。先编码、再保存潜空间、再解码的路径，本来就会分阶段产出。`state.job_id` 仅作辅助，任务状态读 `/api/jobs`；不为此直接读写数据库。

GPU 调查可读取 nvidia-smi 的 UUID、显存、利用率、功耗和温度，多卡分别记录。命令失败或设备离线应记为“未知／不可用”，不能当 0W 样本。功耗窗口和内存占用可作为旁证，不单独触发自动停止。未配置长期监控时使用有界 watch；需要持续观察须按任务授权运行，保留进程与原任务 ID，不能另起生成。

超出同配置历史范围时先查当前阶段、资源竞争、队列错误与进度；正常计算仍在推进就继续等。只有确认错误、资源异常、超过用户明确的时间预算，或多项持续无进展证据足够时，才按任务授权调用 `/api/stop`。停止后等待原任务退出再恢复，避免杀 ComfyUI 或用户其他应用。

工厂可以自启 ComfyUI，也可以复用启动器管理的服务；以当前环境配置为准。自启参数中的卸载策略会影响资源表现，优化需单独验证并记录，不能从另一台机器的经验推出必须关闭工厂自启。
