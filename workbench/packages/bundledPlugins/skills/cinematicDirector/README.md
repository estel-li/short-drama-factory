## 2. 为什么是这样一个结构

原始材料有 **88 KB 的 SKILL 正文 + 169 KB 项目简报 + 18 MB 提示词**。直接塞给模型既读不完也用不好。

所以这里做了三件事：

1. **压成 tip**：每条规则必须有四件东西——祈使句标题、为什么、失效表现、可直接粘贴的英文片段。写不成 tip 的内容一律删掉。
2. **分层**：总概念与分流在 `SKILL.md`（约 13 KB，永远只读这一个），细则拆成 13 个模块，数值与查表拆成 9 张表。
3. **按剧情分流**：`SKILL.md` §3 有一张「剧情卡 → 加载哪些模块」的矩阵。
   **这也是这份 skill 和普通提示词手册最大的区别**：它不是让你读完全部，而是让你先判断这是什么片、然后只读该读的 2–4 个文件。

> **一句话：** 短片只读 2 个文件，长片才读 6 个。读完你应该能回答「我加载了 X，因为剧情卡里 Y＝Z」。

## 3. 怎么用（三步）

**第一步 · 读入口。** 只读 `SKILL.md`。它包含：唯一定理、五步循环、剧情分流表、16 条永远条款、骨架、交付闸门。

**第二步 · 填剧情卡，按分流表加载。** `SKILL.md` §3.1 有 11 格（**风格定位** / **情绪** / 形态 / 时长 / 引擎 / 类型 / 人物负荷 / 场景数 / 驱动力 / 连续性 / 风险标记）——前两格是门把手，缺了先问。填完，照 §3.2 的矩阵开对应模块。

**第三步 · 需要具体数值时开 `banks/`。** 表是查的，不是读的。

```
读请求 → 填剧情卡 → 只加载命中的模块 → 查 banks 取数值 → 过闸门 → 出提示词
```

**两个版本：** 本版是中文版；英文场景用 `cinematic-director` 英文版。结构、条款编号、数字完全相同。

## 4. 每一部分的证据强度（可信度分级）

这份 skill 里的内容不是同等可靠的。请按此分级使用：

| 级别 | 含义 | 大致占比 | 例子 |
|---|---|---|---|
| **A · 硬证据** | 有明确计数 / 原文 / 日志支撑，可复查 | 约 55% | 「300 条真实视频提示词里含独立 `NEGATIVE` 块的是 0 条」；六档视角的距离与结果短语原文；34 条具名失败与修复 |
| **B · 强归纳** | 多个案例一致，但未做全量统计 | 约 30% | 「一镜一类」「先写想要的再写禁止的」「钉板复用只改 10–20%」 |
| **C · 单案例** | 只有一部片这么做，可能是作者个人风格 | 约 12% | 某些 `@TAG` 命名习惯、个别世界观的风格前缀写法 |
| **D · 推断** | 我们的分析，不是原文 | 约 3% | 视角度数换算成毫米数；跨案例的因果关系解释。文中已标 `[推断]` |

**冲突怎么处理的：** 不取平均。当两个来源矛盾时，保留分歧并注明。
例如：CINEDANCE 要求写镜头元数据（毫米/光圈/品牌），而 LIRA 要求写观感结果——本 skill 的处理是**分车道**：剧照/图片车道可用器材词，视频车道只写结果。文中已注明这个冲突，避免下次有人"顺手改回去"。

**三条已记录的偏差（读数前请先知道）：**

1. **行数 ≠ 文本数。** 抓取到的 1,954 行提示词里，重复提交很多。例如 `kok-boru` 的 141 行其实是 **15 条不同文本**；`the-trigger` 125 行是 39 条。所以任何"每分钟多少条提示词"的密度数字都按**去重后**计算，但**块出现率的百分比按行计算**（行＝真实提交次数，更能反映实践）。
2. **每个文件夹最多抓 25 行。** 所以文件夹的计数是**抽样**，不是普查。案例摘要里已按此标注。
3. **`job_set_client_meta` 在大多数案例里为空。** 只有 `zephyr-special` 的 `regenerations` 文件夹带真实的 staging 元数据（`attempt` / `source_job_id` / manifest hash）。其余案例的"第几次尝试"无法从数据里恢复。

## 7. 它明确不做什么

- **不替你写剧本。** 它假设你已经有一个故事或一个场景，负责把它变成能生成的东西。
- **不保证一次成功。** 它保证的是：失败时你知道该改哪一节、为什么。
- **不覆盖配乐/混音/调色。** 声音模块只到"这一镜里有什么声"，后期音频工程不在范围内。
- **不编造没有证据的东西。** 见 `cases/INDEX.md` 第六节「明确不知道的」。
